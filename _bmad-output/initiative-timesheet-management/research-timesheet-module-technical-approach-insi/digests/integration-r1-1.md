# Integration digest r1-1 (identity, reference data sync, payroll handoff, pain points)

Accessed 2026-10-10 for all. Tools: WebFetch worked for RFC 7644, Zoho API limits, BambooHR employee-updated; apidocs.keka.com and docs.bamboohr.com/reference/webhooks returned stub or redirect. Claims marked "search-summary" come from WebSearch result summaries, not a page I read in full, so confidence is capped at med/low. Class: F = fact from official doc, P = pattern/practice, V = vendor-specific behaviour.

## Claims

1. SCIM PATCH (add/remove/replace) is atomic per request; array indexing and JSON Patch move are unsupported; a PATCH adding an already-present value is a no-op that should not bump the modify timestamp (naturally idempotent). | https://www.rfc-editor.org/rfc/rfc7644 | IETF | 2015-09 | med-high (read first 100k of 189k chars; page notes RFC 9865 and 9967 update it) | high | F
2. SCIM pagination is stateless (startIndex 1-based, count); spec says clients MUST be prepared for inconsistent results. Filtering, bulk, sorting, ETag/If-Match are optional and discoverable via ServiceProviderConfig. | same | IETF | 2015-09 | high | F
3. SCIM DELETE may be a soft delete but the server must return 404 afterward and omit the resource from queries; a later user with the same userName must not hit 409. Error model uses scimType (uniqueness, tooMany, invalidFilter...). | same | IETF | 2015-09 | high | F
4. Entra ID SCIM incremental provisioning cycles run about every 40 min (so changes lag); "provision on demand" tests a single user; high error rates put the job into quarantine; failures retry on the next cycle; required attributes (userName, active, name) must stay mapped. Okta retry needs admin intervention per one vendor. | https://docs.delinea.com/online-help/delinea-platform/identity-providers/entra-id/entra-id-scim-provisioning-troubleshooting.htm (and other vendor docs from search) | Delinea / vendor docs via search-summary, not Microsoft primary | n/d | low-med (secondary, no Microsoft page fetched) | V
5. BambooHR employee.updated webhook: payload has type, ISO-8601 timestamp, data.companyId, data.employeeId, data.changedFields (API aliases only). Retries on 5xx up to 5 times with exponential backoff 5/10/20/40/80 min; no retry on 4xx; docs state no ordering, exactly-once or dedupe guarantee; employee.created is followed by employee.updated; history-tracked fields fire when the change takes effect, not when future-dated; API-created webhooks silently do not fire if creator lacks access to all monitored fields. | https://documentation.bamboohr.com/reference/employee-updated-webhook | BambooHR | n/d | high (fetched) | F
6. BambooHR recommends event-based webhooks as a lightweight notification, then fetch current data via API (notify-then-fetch pattern); permissioned webhooks are bound to the creating user's access. | https://documentation.bamboohr.com/docs/permissioned-webhooks and /docs/field-based-webhooks | BambooHR | n/d | med (search-summary) | F/P
7. Keka API: rate limit 50 requests/minute, refilled in 60 s; exceed returns 429 rateLimitExceeded; API module is a paid add-on; only Global admin generates client id/secret (OAuth). | https://developers.keka.com/reference/rate-limit ; https://developers.keka.com/docs/getting-started-with-keka-apis | Keka | n/d | med (search-summary; rate-limit page not fetched) | F
8. Keka PSA endpoints for project tasks, task time entries and timesheet entries (e.g. GET /api/v1/psa/timeentries) appear only in a third-party mirror; employee endpoint details not confirmed. | https://getknit.dev/blog/comprehensive-guide-to-keka-api-directory.md | Knit (third party) | n/d | low | V
9. Zoho People API limits are per plan: Essential 250 calls/user, 5,000/day license max; Professional 250/10,000; Premium 250/15,000; Enterprise 500/25,000. Page states no per-minute limit and no behaviour on exceed. | https://www.zoho.com/people/api/api-limits.html | Zoho | n/d | high (fetched) | F
10. Zoho People to Zoho Payroll is a one-way LOP (loss-of-pay) push, not a raw timesheet feed: user clicks Push to Payroll from Leave > Reports > LOP Reports; Processing Day (LOP cut-off) must be on or before Payday; pay run can't be approved before Processing Day; only employees in the current pay run and on monthly pay periods sync; pay period must match pay schedule; edits in Payroll don't flow back; LOP can be re-pushed after cut-off to run payroll with updated attendance; Zoho People's Leave and Attendance module must be disabled before integrating and can't be re-enabled. | https://www.zoho.com/in/payroll/kb/employer/zoho-people-integration/tips-lop-sync.html ; https://www.zoho.com/in/payroll/help/employer/integrations/integrations-people.html | Zoho Payroll | n/d | med (search-summary quoting docs) | F
11. RazorpayX Payroll lists three attendance modes (dashboard, biometric device, API); GreytHR is listed among supported HRMS integrations via API; the UbiAttendance integration pushes LOP into Payroll in a manual monthly sync and requires the Payroll attendance module be disabled. Nothing found on CSV import specifics or payroll lock. | https://razorpay.com/docs/payroll/attendance ; https://razorpay.com/docs/payroll/integrations/ubitech/ ; https://curlec.com/docs/payroll/integrations/hrms | Razorpay | n/d | med-low (search-summary) | F
12. SAP SuccessFactors: default page size 1000; server-side pagination via skiptoken/__next recommended over client pagination (avoids loss/duplication under concurrent edits); delta by lastModifiedDateTime recommended; effective-dated entities (EmpJob) make the filter unreliable (evaluated across all segments, asOfDate defaults to today), so compare against prior run; recommend max 10 concurrent requests, don't repeat queries far more often than hourly. | SAP KBAs 2920680, 2784034 (login-gated) and https://blogs.sap.com/2023/02/23/how-to-use-lastmodifieddatetime-lastmodifiedon-fields-correctly-in-successfactors-odata-query/ | SAP | 2023 (blog) | med-low (search-summary, KBAs gated) | F/P

SAP KBA says from release 2608 (2026-08-17) soft rate limits and standardised rate-limit response headers (429, Retry-After) apply to all existing tenants; older third-party guide said no strict limits. Merge unified API: rate limits per linked account (Launch 100/min, Professional 400, Enterprise 600); sync intervals depend on provider and plan (standard roughly every 6 h, highest-frequency roughly hourly; Namely lists daily/hourly); Force Resync endpoint and Automatic Webhooks exist for off-interval; recommended pattern is webhooks plus modified_after incremental polling.
